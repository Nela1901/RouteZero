## 1. Evaluación de Alternativas de Stack Tecnológico

| Criterio de Evaluación | Alternativa 1: MERN (Node/Express + React + MongoDB) | Alternativa 2: Python + FastAPI + React + PostgreSQL | Alternativa 3: Java Spring Boot + Angular + PostgreSQL |
|---|---|---|---|
| **Curva de aprendizaje** | Baja (JavaScript unificado en frontend y backend) | Media (Python backend, JavaScript frontend) | Alta (Verboso, fuertemente tipado, configuración compleja) |
| **Integración con algoritmos metaheurísticos** | Baja (Node.js no es el entorno natural para algoritmos científicos) | Alta (Python es el estándar para ACO, GA y metaheurísticas de optimización) | Baja (Java requiere librerías adicionales y mayor esfuerzo de implementación) |
| **Rendimiento de API** | Alto (Node.js asíncrono I/O eficiente) | Alto (FastAPI asíncrono, uno de los frameworks más rápidos en Python) | Alto (Spring Boot robusto pero con mayor consumo de memoria JVM) |
| **Costo de infraestructura** | Moderado | Bajo (FastAPI con bajo consumo de RAM, eficiente en planes gratuitos de Render) | Alto (Mayor consumo de memoria JVM, requiere más recursos en cloud) |
| **Soporte comunitario** | Masivo / Muy alto | Alto / Crecimiento acelerado en los últimos 3 años | Masivo / Corporativo consolidado |
| **Generación automática de documentación API** | Baja (requiere librerías adicionales como Swagger-jsdoc) | Alta (FastAPI genera Swagger/OpenAPI automáticamente en `/docs`) | Media (requiere configuración adicional con SpringDoc) |
| **Compatibilidad con PostgreSQL** | Media (Mongoose está optimizado para MongoDB) | Alta (SQLAlchemy + asyncpg nativos para PostgreSQL) | Alta (Spring Data JPA optimizado para bases relacionales) |
| **Eficiencia energética / Eco-Design** | Media (Node async I/O eficiente pero MongoDB consume más recursos) | Alta (FastAPI asíncrono + PostgreSQL optimizado = menor consumo CPU/RAM) | Media-Baja (Warm-up JVM prolongado, mayor huella energética) |
| **Experiencia del equipo** | Baja (equipo sin experiencia previa en Node.js backend) | Alta (equipo con experiencia en Python y JavaScript) | Baja (equipo sin experiencia en Java enterprise) |
| **Alineación con la consigna del proyecto** | Media (MongoDB no es base de datos relacional requerida) | Alta (cumple todos los requisitos tecnológicos de la consigna) | Baja (Angular y Java no están en la consigna) |
| **Puntaje total (1-10)** | **6.0** | **9.2** | **5.1** |

## 2. Stack Tecnológico Seleccionado

### Decisión: Alternativa 2 — Python + FastAPI + React + PostgreSQL

La Alternativa 2 obtuvo el puntaje más alto (9.2/10) en la evaluación multidimensional, siendo la única que cumple simultáneamente todos los criterios críticos del proyecto.

## 4. Justificación Técnica Formal

### 4.1 Frontend — React.js 18+

React.js fue seleccionado sobre Vue.js y Angular por las siguientes razones:

- **Ecosistema**: Mayor cantidad de librerías compatibles con Leaflet para visualización de mapas interactivos
- **Componentes reutilizables**: Arquitectura basada en componentes facilita el desarrollo del dashboard, mapa y módulos de gestión
- **Comunidad**: La comunidad más grande del ecosistema frontend, con mayor disponibilidad de recursos en español para el equipo
- **Demanda laboral**: Tecnología con mayor demanda en el mercado peruano, aportando valor al portafolio del equipo

### 4.2 Backend — Python 3.11+ + FastAPI 0.100+

FastAPI fue seleccionado sobre Django y Node/Express por:

- **Integración nativa con Python**: El algoritmo ACO (Colonia de Hormigas) y GA (Algoritmo Genético) se implementan en Python, eliminando la necesidad de servicios adicionales de comunicación entre capas
- **Rendimiento**: FastAPI es uno de los frameworks web más rápidos disponibles en Python, comparable con Node.js y Go en benchmarks estándar
- **Documentación automática**: Genera Swagger/OpenAPI automáticamente en `/docs`, cumpliendo el requisito de documentación de API de la consigna
- **Tipado estático**: El uso de Pydantic para validación de datos reduce errores en tiempo de ejecución
- **Eficiencia energética**: Menor consumo de CPU y RAM respecto a Django y Spring Boot, alineado con los principios Green Software

### 4.3 Base de datos — PostgreSQL 15+

PostgreSQL fue seleccionado sobre MongoDB y MySQL por:

- **Modelo relacional**: La naturaleza del proyecto (flota, pedidos, conductores, rutas) se modela naturalmente con relaciones entre entidades
- **Soporte geoespacial**: Extensión PostGIS para manejo nativo de coordenadas GPS y datos georreferenciados del distrito de Huancayo
- **Confiabilidad**: ACID compliance garantiza integridad de datos en operaciones críticas de optimización de rutas
- **Open source**: Sin costos de licenciamiento, alineado con el presupuesto académico del proyecto
- **Row Level Security (RLS) nativo**: Necesario para el módulo de autenticación MFA y gestión de sesiones (ver cambio `add-mfa-sesiones`), donde cada usuario solo debe poder leer sus propios registros de sesión y MFA a nivel de base de datos

### 4.4 Mapas — Leaflet + OpenStreetMap

- **Costo cero**: Sin límites de uso ni costos por API calls, a diferencia de Google Maps API
- **Datos precisos**: OpenStreetMap tiene buena cobertura del distrito de Huancayo y el Parque Industrial de El Tambo
- **Integración con React**: react-leaflet ofrece componentes nativos para React con soporte activo

### 4.5 Algoritmo — ACO (Colonia de Hormigas) + GA (Algoritmo Genético)

- **ACO como algoritmo principal**: Natural para problemas de rutas múltiples (VRPTW), intuitivo de explicar en la sustentación y con buena convergencia para el tamaño del problema (150 pedidos, 15 vehículos)
- **GA como algoritmo secundario**: Se implementa en la Iteración 4 como mejora o comparación de resultados con ACO

### 4.6 Despliegue — Render (backend) + Supabase (base de datos) + Vercel (frontend)

- **Render**: Despliegue del backend FastAPI en plan gratuito, con URL pública estable para la sustentación
- **Supabase**: Hosting de la base de datos PostgreSQL en plan gratuito. Se eligió sobre mantener PostgreSQL directamente en Render por tres razones concretas:
  1. **Colaboración en equipo**: al ser una base de datos compartida en la nube desde el primer día, los 4 integrantes trabajan siempre contra el mismo esquema y los mismos datos de prueba, evitando instalaciones locales de PostgreSQL y el riesgo de "en mi máquina funciona"
  2. **Administración visual de RLS**: Supabase expone un panel donde se pueden inspeccionar y probar las políticas de Row Level Security del módulo de MFA/sesiones sin escribir consultas manuales, útil para un equipo que recién está aplicando RLS por primera vez
  3. **Experiencia previa del equipo**: parte del equipo ya usó Supabase (junto con Render y Vercel) en un proyecto móvil anterior, reduciendo la curva de aprendizaje y el tiempo de configuración inicial
- **Vercel**: Despliegue del frontend React.js en plan gratuito, con URL pública y dominio personalizado para la sustentación
- **Despliegue continuo (Sprint 4)**: el despliegue sale del workflow `deploy-production.yml` de GitHub Actions, que llama a los *deploy hooks* de Render y Vercel (guardados como Secrets de GitHub) solo cuando `ci.yml` y `tests.yml` terminan en verde, y comprueba el sistema después de desplegar. Antes, Render y Vercel desplegaban cada fusión a `main` por su integración nativa con GitHub, sin esperar a las pruebas; en Render esa integración se apagó para que el workflow sea el único camino.

### 4.7 Calidad, pruebas e integración continua

- **Playwright** para las pruebas de extremo a extremo: una sola API para los tres motores de navegador (Chromium, Firefox y WebKit, el de Safari), esperas automáticas, trazas de los casos fallidos, ejecución en paralelo y una imagen oficial que trae los navegadores para ejecutarlas en GitHub Actions sin instalar nada. Las pruebas simulan la API en el navegador para ser rápidas y repetibles, y el monitoreo de producción (Web Vitals, tiempos y códigos HTTP) se ejecuta aparte contra el sistema desplegado.
- **pytest y Vitest** para las pruebas del backend y del frontend, con cobertura medida (meta del Definition of Done: 80 % o más).
- **GitHub Actions** en tres workflows independientes (calidad y compilación, pruebas y despliegue) en lugar de uno solo, para que cada etapa tenga su propio resultado, sus propios informes y se pueda reutilizar como condición del despliegue.
- **Análisis de calidad y seguridad:** SonarQube Cloud, Bandit y pip-audit en el backend; oxlint y npm audit en el frontend; Lighthouse CI y el validador W3C para rendimiento, accesibilidad y HTML.

## 5. Decisiones Arquitectónicas

| Decisión | Elección | Justificación |
|---|---|---|
| Arquitectura del código | Por características | Módulos independientes (flota, pedidos, rutas, algoritmo, dashboard) facilitan el trabajo paralelo del equipo y la mantenibilidad |
| Patrón de acceso a datos | Repository | Desacopla la lógica de negocio del acceso a la base de datos, mejorando la mantenibilidad a largo plazo |
| Flujo de trabajo Git | Feature Branch Workflow | Cada integrante trabaja su módulo en rama propia e integra cambios via pull request, evidenciando colaboración distribuida |
| Algoritmo principal | ACO (Colonia de Hormigas) | Natural para problemas de rutas múltiples, intuitivo de explicar en sustentación y con buena convergencia para el tamaño del problema |
| Algoritmo secundario | GA (Algoritmo Genético) | Implementado en Iteración 4 como mejora o comparación de resultados con ACO |
| Pruebas de extremo a extremo | Playwright en tres navegadores con la API simulada, más monitoreo real de producción aparte | La simulación hace las pruebas rápidas, repetibles y capaces de provocar fallos a voluntad; el monitoreo cubre lo que solo se ve en producción (tiempos, disponibilidad y códigos HTTP) |
| Despliegue | Workflow de GitHub Actions con *deploy hooks* en vez de la integración nativa de Render y Vercel | Solo se despliega si el CI y las pruebas terminan en verde; los accesos viven como Secrets de GitHub y no en el repositorio |
| Auditoría de dependencias en CI | Bloquea por vulnerabilidades altas o críticas de las dependencias que se despliegan; las de desarrollo se auditan sin bloquear | Una vulnerabilidad de severidad alta en una herramienta de desarrollo sin versión corregida bloqueó todos los Pull Request, aunque no afecta a lo que se despliega |
| Hosting de base de datos | Supabase (en vez de PostgreSQL directo en Render) | Base de datos compartida en la nube para todo el equipo desde el inicio del desarrollo, administración visual de RLS y experiencia previa del equipo con la plataforma |
